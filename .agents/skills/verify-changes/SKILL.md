# Verify changes

The `main` branch syncs to Lovable and deploys from there, so every commit must
leave the site in a working state.

## 1. Run the checks

Run all four checks and keep going after a failure, so you see every problem at once:

```sh
bun run lint
bunx tsc --noEmit
bun run test
bun run build
```

- Fix the errors your change introduced. Do not silence a rule with
  `eslint-disable` or `@ts-ignore` unless you explain the reason in a comment.
- **Known lint baseline:** much of the existing code (generated by Lovable) is
  not Prettier-formatted, so `bun run lint` already reports many
  `prettier/prettier` errors on `main`. Do not reformat the whole repo as part
  of an unrelated task. Instead, lint only the files you changed, for example
  `bunx eslint src/routes/things.tsx`, and make those files clean. On Windows
  with `core.autocrlf=true`, ignore `Delete ␍` errors: they come from the
  checkout, not from the committed files.
- If a check already failed before your change, say so in your report instead of
  fixing unrelated code.
- `src/routeTree.gen.ts` is regenerated by the dev server or the build. If you
  added or removed a route, run the build so the file updates, and commit the
  regenerated file.

## 2. Review the diff

Run `git diff` and check:

- [ ] No edits to generated files (`routeTree.gen.ts` excepted when regenerated,
      `src/integrations/supabase/types.ts`, `src/components/ui/*`, `drizzle/meta/*`).
- [ ] No content hard-coded into components; content belongs in the database.
- [ ] No secrets, service-role keys or new `.env` values.
- [ ] New public routes have a complete `head()`: title, description, og tags.
- [ ] Database changes come as a new migration file with RLS. Old migrations
      are unchanged.
- [ ] No leftover `console.log` or debug code.

## 3. Report

State which checks passed, which failed and why, and anything you could not
verify, for example a migration that only Lovable Cloud can apply.
